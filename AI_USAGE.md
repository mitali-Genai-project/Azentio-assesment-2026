# AI usage

## Tool

**Claude Code** (Anthropic, model Claude Opus 5.5), used as a coding agent inside VS Code on Windows. The
agent read and wrote files, ran Maven, pytest and Python scripts, and installed Python 3.12 after I approved it.

## How it was used

I gave one detailed brief (role, stack, the three tasks, engineering standards) and asked the agent to work
in five phases, stopping after each one with a report of changed files, decisions, test results and open
issues before I approved the next phase.

### Important prompts

1. **Main brief** (summarised). Act as a senior Java full-stack engineer and build Clearlist:
   - Spring Boot 3, PostgreSQL/Flyway, Redis behind an interface, Spring Security;
   - FastAPI with a deterministic fake LLM provider;
   - tasks in priority order (Task 1 at 50%, Task 2 at 30%, Task 3 at 20%).

   Key constraints: work in phases and run tests each phase; do not fabricate test, performance or
   integration results; `mvn test` and `pytest` must run offline; keep no secrets in the repo; do not commit;
   report incomplete requirements clearly.
2. **Python installation**: when the agent found Python was missing, it asked how to proceed and I chose
   "install via winget". winget could not run from the agent's shell, so the agent used the official
   python.org installer (user scope) instead, after checking its signature.
3. **Phase approvals**: "yes go ahead" after reviewing the Phase 2, 3 and 4 reports. With the Phase 3
   approval I also shared two reference images (a screening dashboard and the architecture diagram).
4. **Cross-check against the assessment PDF**: "please verify and cross check with this pdf requirement that
   everything is implemented as expected?". My original brief to the agent was a paraphrase of the PDF;
   this check found the gaps listed in rows 11–14 below.
5. **"Yes fix these issues and I need to push this code into my branch feature/core-functionality"**: the
   agent fixed the gaps, re-ran both test suites, then created the commits and pushed the branch.

## Code generated with AI assistance

The large majority of the code and documentation in this repository was generated by the agent:

- **Java backend**: all of `backend/` (entities, Flyway migrations, services, matcher, cache, security,
  audit, controllers, exception handling, all tests) and the Maven wrapper.
- **Scripts**: `scripts/generate_watchlist.py` and `scripts/load_test.py`.
- **Python service**: all of `python-summary/` (service, prompt template, validator, tests).
- **Infrastructure and docs**: `docker-compose.yml`, `.env.example`, `.gitignore`, `README.md`, this file.
- **Data**: `data/*.csv|json` are output of the generator script, not hand-written.

## Errors and incorrect suggestions from the AI, and how they were caught

Everything below happened during this build. Most were caught by tests the agent ran; some by the agent
re-reading its own code before running it.

| # | What was wrong | How it was detected | Fix |
|---|---|---|---|
| 1 | The data generator picked honorifics with Python's `hash()` of a string, which is randomised per process, so the dataset would differ between runs. | Agent review before the first run; determinism then confirmed by generating twice and comparing file hashes. | Index derived from the entry id. |
| 2 | First matcher design: a single-token name was compared with the other name's concatenated form, and the token threshold was 0.80. Evaluation gave recall 1.000 but **false-positive rate 0.360** (e.g. `Kozlov` matched `Yuri Kozlov`, `Nabil Rao` matched `Anil Rao`, `Xiaoming Zhang` matched `Xiaoming Huang`). | `MatchingEvaluationTest` failed its FPR assertion. | Measured Jaro-Winkler on real transliteration pairs vs confusable pairs. Raw scores could not separate them (`zhang/chang` and `zhang/huang` both 0.867), so the agent added transliteration folding, a single-token rule, exact matching for ≤ 3-letter tokens and a 0.88 token threshold. |
| 3 | Jaro-Winkler's prefix bonus made `Ivan Petrov` match `Aleksandr Ivanovich Petrov` (`ivan` ≈ the patronymic `ivanovich`). The evaluation dataset did not contain this case. | Unit and API tests failed. | Token pairs whose length ratio is below 0.6 cannot match. Added a named regression test. |
| 4 | A test expected the 3-part primary name to be reported, but the 2-part alias legitimately scored higher. The test was wrong, not the code. | API test failure. | Test input changed to the full 3-part name. Best-name-wins behaviour kept. |
| 5 | Screening responses read entry details through lazy JPA proxies, which would cost one extra SELECT per hit. | Agent review. | DTOs built from the in-memory match result instead. |
| 6 | An audit append-only test was written so it could pass without asserting anything (only ran if an audit row already existed). | Agent review. | Rewritten to create its own hit and disposition, then attempt a delete and an edit. |
| 7 | The load test made "unique" names by appending digits, but the server's normaliser strips digits, so unique names would collide in the cache and inflate the hit ratio. | Agent review; then verified 495 distinct names in 1,000 requests. | Letters-only suffix. |
| 8 | The FakeProvider's closing sentence ("…are the same person…") would have been rejected by the agent's own "match conclusion" validator, so every fake summary would have fallen back. | Agent review before running the tests. | Sentence reworded; the round-trip test now guards it. |
| 9 | The agent initially added an `ANTHROPIC_API_KEY` placeholder to `.env.example` for a real provider it then decided not to build. | Agent review in Phase 4. | Placeholder removed so the config does not advertise a missing feature. |
| 10 | The generated `mvnw.cmd` fails when the user path contains a space. | Failed when run. | Not fixed. Documented workarounds: plain `mvn`, or `./mvnw` from Git Bash. |
| 11 | The three name pairs the PDF explicitly names (`Aleksandr Petrov`/`Alexander Petroff`, `Dr. Chen Wei`/`Wei Chen`, `J. R. Fernandes`/`Joao Ricardo Fernandes`) were not in the tests. The agent had flagged that it did not have the assessment's examples, but never asked for them. | Cross-check against the PDF. | Added as named test cases; all three pass. |
| 12 | The Maven project lived only in `backend/`, so the graders' plain `mvn test` at the repo root would have failed with "no POM". | Cross-check against the PDF's "we will run `mvn test`" rule. | Root aggregator `pom.xml`; `mvn test` from the root verified (128 tests pass). |
| 13 | The agent skipped the optional real LLM provider, but the PDF's "done" list requires the README to show how to switch to one. | Cross-check against the PDF. | Added `OllamaProvider` (standard-library HTTP, no API key) with mocked-HTTP tests and README instructions. |
| 14 | No unit test directly asserted "the cache key changes when the list version changes"; only indirect version-isolation tests existed. | Cross-check against the PDF. | Added `cacheKeyChangesWhenListVersionChanges`. |

A further, minor one: a throwaway `jshell` experiment had broken regex escaping in a shell `sed` command,
which made some of its measured numbers misleading. Only the subsequent Java unit tests were relied on.

## Git history

I had told the agent not to commit while it worked, so that I could review each phase first. As a result the
work was **not committed incrementally**: the commit history was created at the end of the session, after
the 13:30 IST deadline. The work was split into focused Conventional Commits by area so the history is
readable, but the commit timestamps show when they were made, not when each piece was written.

## What was **not** verified

Docker was not available, so none of these were run:
- integration tests against real PostgreSQL and Redis;
- the Spring Boot app started against PostgreSQL;
- the load test;
- `EXPLAIN` output for the review-queue query.

The README marks each of these as not run, and no results are claimed. The evaluation figures are on a
synthetic dataset generated in this same session, and the matcher was tuned after seeing failures on it
(README §13).
